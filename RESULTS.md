# Results

Every number below came from a command in this file, on this machine
(Windows 11, Python 3.12.1, standard library only). Everything is seeded;
re-running any command reproduces the figure exactly.

---

## 1. The test suite

```bash
python test_scheduler.py
```

**15 / 15 passed**, 0.4 s. No pytest, no network, no fixtures on disk.

Three of the fifteen are the invariant itself, run against all five
algorithms: two fixed workloads and 200 seeded random ones (`Random(42)`,
1–8 processes, arrivals 0–15, bursts 1–9, quanta from {1, 2, 4, 7}). That is
1000 algorithm runs per suite execution, each one checked slice by slice.

`test_invariant_catches_a_deliberately_broken_timeline` is the load-bearing
one. It feeds `validate_timeline` two timelines that are wrong in different
ways and fails if either is accepted:

| Corruption | What it simulates |
|---|---|
| every slice shortened by one unit | a scheduler losing time on each context switch |
| `P2` scheduled at t=0 when it arrives at t=1 | a process running before it exists |

Without this test the suite would prove nothing about the checker the other
tests depend on.

## 2. The classic workload, all five algorithms

```bash
python cli.py workloads/classic.json
```

The worked example from the Silberschatz scheduling chapter — four processes,
arrivals 0/1/2/3, bursts 8/4/9/5 — so the expected figures come from a source
outside this repo.

| Algorithm | Avg waiting | Avg turnaround | Avg response | Context switches |
|---|---|---|---|---|
| FCFS | 8.75 | 15.25 | 8.75 | 3 |
| SJF (non-preemptive) | 7.75 | 14.25 | 7.75 | 3 |
| **SRTF (preemptive)** | **6.50** | **13.00** | **4.25** | 4 |
| Round Robin (q=4) | 11.75 | 18.25 | 4.50 | 7 |
| Priority | 7.75 | 14.25 | 7.75 | 3 |

SRTF wins on every metric here and pays one extra context switch for it. Round
robin has the *worst* average wait and the second best average response — which
is the entire point of round robin and the reason both numbers are reported.
Optimising for average wait alone would rank it last and hide the fact that it
answers every process within 4.5 units.

Priority and SJF tie exactly, because in this workload the priority order
happens to be the shortest-job order. That is a coincidence of the fixture,
not a property of the algorithms.

## 3. Idle time is real time

```bash
python cli.py workloads/idle-gap.json --algo fcfs
```

Nothing arrives until t=5, and there is a hole between t=9 and t=20.

| Figure | Value |
|---|---|
| First slice starts at | t=5 |
| Makespan | 25 |
| Busy | 9 units |
| **CPU utilisation** | **36.0%** |
| Avg waiting | 0.667 |

The tempting bug is to start the first process at t=0, which silently hands it
five free units, drives utilisation to 100% and makes every waiting figure in
the table too low. `test_the_cpu_idles_instead_of_time_travelling` pins the
0.4444 utilisation of a smaller version of this case.

## 4. The recommender against the default it replaces

```bash
python bench.py                  # 500 workloads per shape, seed 42
python bench.py --json           # same numbers, machine readable
```

**Baseline:** round robin, quantum 4 — what an operator picks without thinking
about it. **Candidate:** `scheduler.recommend()`, which simulates all five
algorithms plus round robin at quanta 1, 2, 4 and 8, and returns whichever
gives the lowest average waiting time.

1500 seeded random workloads across three shapes:

| Shape | Baseline avg wait | Searched avg wait | Reduction | Better | Same | **Worse** | Median search |
|---|---|---|---|---|---|---|---|
| uniform | 14.363 | 8.483 | **40.9%** | 482 | 18 | **0** | 0.512 ms |
| bursty | 9.952 | 5.090 | **48.9%** | 417 | 83 | **0** | 0.561 ms |
| batch | 45.609 | 23.616 | **48.2%** | 499 | 1 | **0** | 0.783 ms |

The **worse column is zero in all three shapes**, which is the claim worth
making: the search is never a downgrade, because the baseline is one of the
candidates it evaluates. `test_recommend_never_loses_to_the_default` asserts
this on 100 further workloads, so a regression fails the suite rather than
quietly costing wait time.

Workload shapes, all generated by `bench.py`:

- **uniform** — 3–10 processes, arrivals 0–20, bursts 4–8
- **bursty** — same, but 25% of processes get a burst of 15–30 and the rest 1–4
- **batch** — everything arrives at t=0, bursts 1–25

### What it picked, and why that is the interesting result

| Shape | Choices |
|---|---|
| uniform | `sjf` ×307, `srtf` ×108, `fcfs` ×85 |
| bursty | `srtf` ×343, `fcfs` ×83, `sjf` ×63, `rr(q=2)` ×6, `rr(q=1)` ×4, `rr(q=4)` ×1 |
| batch | `sjf` ×481, `fcfs` ×19 |

**The baseline almost never wins.** Round robin at quantum 4 was chosen
**1 time out of 1500**, and round robin at any quantum only 11 times, all of
them in the bursty shape. The default most people reach for is close to the
worst available option on this metric.

Two honest caveats on that:

1. **The metric is chosen, and it favours SJF by construction.** SJF is
   provably optimal for average waiting time on a fixed job set, so a search
   scored on average wait is close to a search for "which of these is SJF
   today". Score the identical 1500 workloads on `avg_response` instead and the
   ranking inverts completely:

   | Metric | What wins | Baseline `rr(q=4)` | Searched |
   |---|---|---|---|
   | `avg_waiting` | `sjf` 851, `srtf` 451 | 23.31 | 12.40 |
   | `avg_response` | **`rr(q=1)` 1369**, `srtf` 71 | 6.836 | **1.774** |

   Round robin does not lose because it is bad. It loses because average wait
   is not the job it is for — on the metric it *is* for, it wins 91% of the
   same workloads. Reproduce with `--metric avg_response`.
2. **`fcfs` appearing at all is a tie, not a win.** When every process arrives
   together with equal bursts, all five produce the same wait, and
   `recommend()` breaks the tie on fewest context switches, which FCFS wins.
   That is deliberate: equal wait time should go to the cheaper schedule.

### Cost

Median 0.5–0.8 ms to evaluate nine candidates on a 3–10 process workload, on
one core, no parallelism. The search is O(candidates × total_burst ×
processes), so it scales with the length of the workload rather than the
number of algorithms. At the size this simulator is for, searching is
unambiguously cheaper than being wrong.

## 5. Where this does not apply

**These are simulated processes, not measured ones.** Every burst time is
known exactly and in advance. Real schedulers cannot see burst times, which is
why no production kernel runs SJF or SRTF — they *estimate* the next burst
from history and get it wrong. A 48.9% reduction against a real workload with
estimated bursts would be a different and much smaller number, and this project
does not measure that.

**No I/O, no blocking, no multi-core.** Every process is pure CPU on one core.
Adding an I/O burst introduces a blocked state and a second queue and changes
the arithmetic of all five algorithms.

**Priority scheduling starves.** `workloads/bursty.json` has four priority-1
processes; a priority-5 process behind them waits for all of them, every time.
There is no aging. That is left visible in the output rather than papered over,
because starvation is the thing about priority scheduling worth seeing.
